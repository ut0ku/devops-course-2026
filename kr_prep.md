## 1. Когда rebase, а когда merge?

**Rebase** - для личных feature-веток, которые ещё никто не видел, даёт линейную историю без лишних merge коммитов, например: перед созданием PR

**Merge** - для публичных веток (main, dev), не переписывает историю, безопасен для командной работы, например: слияние feature в main после Code Review

**Правило:** rebase - для локальных, merge - для публичных

## 2. Что будет, если сделать rebase публичной ветки?

Rebase **переписывает историю** - у коммитов меняются хеши, если ветку уже скачали коллеги:
- У них останутся старые коммиты, у тебя - новые
- При git pull возникнут конфликты и раздвоение истории
- Им придётся вручную восстанавливать ветку, что может привести к потере изменений

Золотое правило: не делать rebase публичных веток

## 3. Зачем нужен multi-remote?

Это несколько удалённых репозиториев для одного локального, позволяет пушить одной командой сразу в несколько мест

**Сценарии:**
1. **Зеркало для бэкапа** - основной на GitHub, копия на GitLab
2. **Форки в OpenSource** - origin (свой форк) и upstream (оригинал)
3. **Миграция** - временный push в оба репозитория при переезде
4. **Разные команды** - одна на GitHub, другая на GitLab
